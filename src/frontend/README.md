# Frontends

The desktop product has three native surfaces over the same Zig reader/model:

- `dict`: CLI
- `dict tui`: terminal UI
- `dict-qt`: Qt 6 / C++ desktop GUI

There is no HTTP or browser frontend in the product binary.

## C ABI

`src/frontend/c_api.zig` exposes an opaque C handle through `src/ffi/dict.h`.
The Qt application links to `libdictffi` and calls the Zig core in-process.

The ABI intentionally returns versioned UTF-8 JSON buffers (`dict.results.v1`) instead of exposing Zig structs. This keeps the C boundary stable while the internal presentation model evolves.

The handle owns a mapped dictionary/index and one persistent native Lua expansion worker. Search, lookup and random-word requests therefore do not spawn the CLI or use IPC except for the existing native expansion worker protocol.
## Native Lua expansion

Lua expansion has one implementation: the dump-specific `dict-native-expansion-worker` generated by the coordinated build. Missing or incompatible runtime assets are explicit failures; no VM/interpreter fallback exists.

Core language blobs may defer large sections into companion blobs. Full lookups resolve those companions; `--core-only` intentionally reads only the compact core and labels omitted material.

`--with-source` includes exact source in JSON. `--format source` emits only source bytes.

## Qt application

Build the native GUI with:

```sh
zig build qt
```

Qt uses Widgets and C++20. History, bookmarks, learning scores and UI settings are persisted locally with `QSettings`. Definition quizzes, flashcards, unscramble, and random-word navigation all consume the same native dictionary data.
